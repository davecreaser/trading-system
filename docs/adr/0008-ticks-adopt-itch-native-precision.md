# Ticks adopts ITCH's native $0.0001 precision

Epic 1 defined `Ticks` as "an integer count of the instrument's minimum price increment" without pinning down what that increment actually is in real terms. Integrating real ITCH data forced the question: ITCH's `Price(4)` fields are 4-byte integers with 4 implied decimal places ($0.0001 precision). We considered converting to the standard US equity minimum increment ($0.01, dividing ITCH's raw value by 100), which matches "tick = minimum increment" more literally, but rejected it: non-displayed/hidden orders can legitimately execute at sub-penny prices (Reg NMS Rule 612 only mandates whole-penny increments for displayed quotes on stocks over $1, not for midpoint/hidden execution prices), which shows up specifically in `Order Executed With Price` — exactly the message used for validation against real fills. A clean divide-by-100 would either truncate that precision or require special-case handling for sub-penny values. Adopting ITCH's native $0.0001 precision directly sidesteps the sub-penny question entirely (no rounding, no lost precision, no conversion math at all) and remains fully consistent with ADR-0005's actual requirement (exact integer comparison, no floating point) — it just means a "tick" in this project is finer than a real-world cent, a naming mismatch rather than a correctness issue.
