# Feed Parser: three-layer architecture (framing, decoding, book-driving)

Parsing ITCH and driving the order book with it has three genuinely distinct concerns: splitting the raw file into individual messages (framing — a transport convention, not part of the ITCH spec itself), decoding one message's bytes into a strongly-typed representation (wire-format knowledge only, nothing about trading semantics), and applying decoded messages to the `OrderBook` (trading semantics — symbol filtering, ITCH-reference-to-`OrderId` mapping, translating ITCH operations into `add`/`cancel`/`modify` calls). We kept these as three separate layers rather than one class that does everything, because each has a different reason to change and a different testability need: framing can be tested against a handful of hand-built byte sequences with zero knowledge of what a message means; decoding can be tested the same way, independent of `OrderBook` entirely; book-driving can be tested against pre-decoded messages without needing real bytes at all. Decoded messages are represented as a `std::variant` over a closed set of message-type structs (only the types the book-driving layer or the validation step actually acts on are fully modeled — Stock Directory, Add, Cancel, Delete, Replace, Executed, Executed With Price; the other ~13 ITCH message types get a thin catch-all, since the framing layer already knows each message's length regardless of its type) rather than a class hierarchy with virtual dispatch, since the set of types is fixed and known — `std::variant` avoids per-message heap allocation and vtable dispatch, and `std::visit` gives compile-time exhaustiveness checking for free.
